## Workspace map

- `web/`: React/Vite portal; source under `web/src/`, tests under `web/test/`.
- `mobile/flutter/`: Flutter client; source under `lib/`, tests under `test/`. Run Flutter commands here.
- `backend/backend/api/`: PHP API and runtime database behavior.
- `backend/`: includes schema/support artifacts; confirm runtime versus thesis schema in the Database document before a schema change.
- `scripts/`: launch, deployment, backup and verification helpers. Inspect a script before running it; some setup/demo/smoke/restore scripts modify existing data.
- `docs/`: the context bundle plus client evidence, product notes, thesis and handover materials.
- `.runtime/`: local dated screenshots/reports and temporary verification evidence. Do not expose raw logs containing sessions, credentials or tokens.

Do not assume this checkout has Git or that an old absolute path in a README is current. Inspect the workspace and current processes before choosing a launch or worktree strategy.

## Product invariants

1. SmartFlow tracks physical inter-office folders. It is not a financial approval engine or a digital-document storage replacement.
2. A request is a formal ticket; accepting or linking it does not record a physical handoff or complete the ticket.
3. Register a folder already held by the registering office. Request it when another office holds it.
4. QR/ID lookup verifies/finds a folder; only the explicit confirmed action records IN, OUT or filing.
5. Preserve expected-movement checks, duplicate/stale-write protection, receipt confirmation and counted folder-content rules.
6. Preserve the DV flow through Engineering, Budget, Accounting, Treasury, Mayor and Treasury, including the applicable optional Accounting return. Check the actual routing helper before changing type-specific completion behavior.
7. Treasury's payment-release ticket action is distinct from Accounting acceptance, custody receipt and folder completion.
8. Accepted requests can remain overdue until fulfilled; date-only request deadlines include the due day.
9. Keep full request purpose, decline/closing notes, correction reasons and linked custody history available to permitted users.
10. Keep client/server permission discrepancies visible. Monitor-only presentation is not server-side authorization, and broad server role gates do not by themselves establish accepted product intent.
11. Registration, IN/OUT and filing are staff-only on the API and clients. Preserve separate head/admin request, checklist, deadline and report authority; mobile checklist management lives outside physical registration.
12. Preserve request row locking and displayed status/revision guards, shared link/close evidence checks, creation-operation recovery and server-paged listings/history. Never replace complete logs with dashboard previews or automatically retry an uncertain creation with a new ID.
13. Destination recording correction is limited to sending-office staff and the latest unreceived OUT. Preserve displayed movement/destination/correction guards, full reason/confirmation, saved-outcome recovery, previous-holder return rules and completed DV constraints. Append old/new destination evidence; never fabricate a receipt or change original event ID/time/counts.
14. Keep session tokens in authentication headers for JSON, multipart, exports and labels. Signup status needs owner proof; explicit logout revokes the presented session, password change/deactivation revoke existing sessions, and reactivation does not revive old tokens. Preserve matching-login cleanup and re-sign-in behavior.
15. Approved legacy signup-status ownership uses immutable `approved_user_id` and current active-account credentials. Preserve request-code access after rename; never infer a historical NULL binding from a reused username. An approved request without key or binding requires administrator assistance.

## Working method

1. Identify the intended outcome, role, platform and existing behavior.
2. Inspect the relevant context and narrow source paths; prefer fast text/file searches.
3. Make scoped changes that preserve existing user work and accepted preferences. Avoid broad reformatting, generated platform rewrites and unrelated dependency upgrades.
4. If delegating, assign disjoint file ownership and inspect every result before integration.
5. Verify the behavior with checks appropriate to the change. For visual work, inspect actual browser/emulator screenshots, including long text and empty/error states.
6. Explain the resulting behavior, evidence and material limitations. Keep historical test results separate from checks run in the current turn.
7. Update affected context documents when a confirmed requirement, flow or implementation changes.

Routine reversible work within the user's authorized task should proceed without redundant permission questions. Consequential external actions and destructive changes require the applicable authorization; complete a reviewable result before seeking any final approval that is actually needed.

## Data and environment discipline

- Preserve current database records, accounts and application sessions. Do not reseed, purge, restore or sync over the running system as a routine launch or test step.
- Before installing a review APK, inspect its API/build configuration and explicitly build with `FORCE_LOGIN_ON_START=false`; development defaults otherwise clear the saved sign-in on cold start. `adb install -r` alone does not prevent this application-level clearing. Preserve app data and never uninstall/reset to resolve an update failure.
- Use the in-memory web UI review fixture for sample interactions. Use the isolated database harness described in Testing for API mutations.
- Do not run `scripts/smoke-test.ps1` against the user's current database without intentionally choosing an isolated copy; it is a mutating script.
- Keep credentials, `.env` contents, QR secrets, bearer/reset tokens and personal data out of source, docs, terminal output and shared screenshots.
- Do not alter global SDK/OS settings just to produce a screenshot; restore temporary viewport/font overrides after testing.
- Use the current configured API base. Local web and Android emulator addresses differ; the emulator's `10.0.2.2` reaches the host PC.
- An ambiguous write failure must not cause an automatic retry that could record a duplicate handoff.
