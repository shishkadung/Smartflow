# SmartFlow code style and change rules

Last reviewed: **15 October 2026**. This document describes the checked-in source and sets rules for future work. It does not authorize an application redesign or change a workflow requirement. ## Rules for new changes

1. **Keep changes scoped.** Edit the feature and its shared dependencies only when necessary. Do not reformat whole Dart files, replace frameworks, regenerate lockfiles, or upgrade unrelated packages during a UI fix.
2. **Use existing seams.** Put reusable presentation in components/widgets and pure logic in utilities/helpers. Use the existing API facade rather than adding direct fetch/HTTP calls to each screen. Keep endpoint and database decisions out of presentation components.
3. **Name the domain precisely.** A request, physical folder, custody movement, receipt and payment release are different records/events. Preserve these distinctions in variables, messages and labels. Human UI labels may say “Accepted” while stored/API status remains `approved`; do not rename the contract to match display copy.
4. **Use existing theme and icons.** Reuse shared colors, type styles and component patterns. Scope page-specific web CSS to a page class under `.app-shell`; check desktop and phone breakpoints. Preserve stylesheet order unless changing the cascade is necessary within the current task; explain the change and verify affected pages.
5. **Keep UI state separate.** Loading, saving, empty, unavailable and failed states need different behavior. A failed read must not show a verified empty result. Disable conflicting actions during a write and preserve drafts during refreshes.
6. **Use semantic controls.** Navigation uses links; actions use buttons. Provide labels, keyboard selection, focus restoration and accessible dialogs. Long details must scroll without hiding required actions. Follow [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md) for layout rules.
7. **Add useful comments.** Explain a domain constraint, recovery behavior or non-obvious dependency. Avoid comments that simply repeat the next line of code. Keep documentation synchronized when a contract or workflow changes.

## API and data rules

- Protected web views obtain `smartflow`, `api`, exports and printable labels from `useAuth()` so asynchronous callbacks retain the reviewed login. Keep pre-dispatch and post-body session checks; reset prior views/dialogs on shared identity changes. Preserve the original account's uncertain creation operation across login changes. Public sign-in/signup/recovery may use the unbound facade.
- Never return recovery codes or delivery metadata in public responses, even in development. Legacy maintenance must reject HTTP before configuration/bootstrap; CLI operation requires explicit environment and operation opt-ins. Launch helpers must not deploy, seed, mirror operational folders or sign in automatically.

- Enforce authorization and validation on the backend. Hiding a control in either client is not sufficient authorization. Derive the acting user/office from the authenticated session on the server. Reconcile the permission gaps in PRD/Security against intended product roles; an existing permissive gate does not approve broader access.
- Preserve documented JSON keys, status values and optional-field omission. IDs such as `DOC-2026-000001` are opaque tracking references, not integers. Validate numeric office/request IDs before use.
- Keep structured error details (`scan_error`, `qr_error`) available to recovery screens. A generic message must not remove a recoverable domain error.
- Distinguish authentication expiry from ordinary office access denial. An old response must not clear a newer saved login. See [web/test/session-events.test.mjs](../web/test/session-events.test.mjs) and [mobile/flutter/test/session_refresh_test.dart](../mobile/flutter/test/session_refresh_test.dart).
- Use parameterized PDO SQL for user input. Do not build SQL by interpolating user text. Explicitly validate bounded strings, calendar dates, IDs, inventory and receipt contents.
- Do not log authentication tokens, signup ownership keys, passwords or recovery codes. Session transport is header-only, including multipart, exports and printable labels; do not restore query/body fallbacks or token-bearing links. Keep the compatibility authentication headers for supported Apache/CGI deployments and verify forwarding. Sanitize diagnostics and screenshots, including historical logs that predate this change. See [SECURITY.md](SECURITY.md).
- Public request codes/usernames are identifiers, not signup-status ownership proof. Use the POST status-key contract; legacy NULL-key requests require freshly entered credentials and must not retain passwords for polling or persist them in navigation/storage. Approved legacy ownership binds to immutable `approved_user_id`, never a mutable username; do not guess historical NULL bindings. Check mounted state before async native field cleanup.
- Complete server logout before reporting explicit sign-out success; end only the matching client login so a delayed response cannot clear another session. Password change requires reauthentication after server revokes all user sessions. Account reactivation must not revive old tokens.
- Native profile forms and photo pickers retain the original API/token/user before asynchronous work; recheck identity before dispatch and response application. `AuthProvider.refreshUser` requires the originating token and matching response user. All session preference writes/clears share the serialized persistence path. A pending logout blocks new profile writes, but a successful existing response for that unchanged login still applies if logout fails.
- Native sign-in screens own/cancel their pending login attempt. Persist a candidate token/user pair through the serialized preference path before publishing it; cancelled or failed candidates restore the committed pair rather than an optimistic candidate snapshot. A replacement token/user/office/role resets protected page state and removes that login's root and shell popup routes; same-token profile refresh must preserve current work.
- Protected native dialogs, sheets and submissions retain the originating API/token/user before asynchronous work. Check the same login and no pending logout before dispatch, including after confirmation. For a response or busy-state cleanup, require the same login and mounted page; a pending logout alone must not discard an already-submitted outcome when logout fails. Guard deferred snackbar actions too. Navigation after a submitted operation must not erase uncertain recovery or repeat the write.
- Use the configured municipal timezone for deadlines and report periods. A date-only deadline covers the end of its day. Preserve API-provided timestamps/display semantics rather than silently shifting a deadline through browser UTC conversion.

## Workflow invariants that code style must protect

| Invariant | Implementation references |
|---|---|
| Accepting or linking a request does not receive, move or complete the physical folder. Accepted open requests remain overdue until completed; terminal request states stop request overdue. | [document-requests-helper.php](../backend/backend/api/document-requests-helper.php), [document-requests-update.php](../backend/backend/api/document-requests-update.php) |
| Registration is staff-only and uses the physical holder's assigned office. Head/admin monitoring, request handling and checklist management remain separate permissions. A linked registration creates the document, initial custody and request link atomically. An invalid link must leave no orphan folder/movement. | [documents-create.php](../backend/backend/api/documents-create.php), [test-request-linking.php](../scripts/test-request-linking.php), [PRD](PRD.md) |
| IN/OUT writes use current custody state and server locks. System receipt requires confirmation of actual receipt; a stale view cannot silently overwrite the latest movement. | [movements-create.php](../backend/backend/api/movements-create.php), [movement-requests-helper.php](../backend/backend/api/movement-requests-helper.php) |
| Correction returns require a reason and a valid previous holder. Do not replace custody history with the nominal DV route. Shared client validation currently requires a 5–200 character return reason. | [web/src/tracking.js](../web/src/tracking.js), [routing-helper.php](../backend/backend/api/routing-helper.php) |
| Correcting a recorded destination is distinct from a physical return. Only sending-office staff may correct the latest unreceived OUT, with movement/destination/correction revision guards, explicit confirmation and a 5–1000 character reason. | An interrupted movement must be checked before another IN/OUT. Never automatically repeat an uncertain write. | Linked-folder navigation opens exact Documents detail; History is secondary. Out-of-tray fallback follows only a 404, stays authenticated/read-only and propagates access denial. Do not expand custody or visibility permission to shorten navigation. | [web/src/document-detail.js](../web/src/document-detail.js), [mobile/flutter/lib/screens/shared/documents_screen.dart](../mobile/flutter/lib/screens/shared/documents_screen.dart) |
| The DV journey normally follows ENG → BUD → ACC → TRE → MAY → TRE, with an optional final return to ACC. First Treasury receipt is not final completion. Filed non-DV folders must not acquire a DV-only return action. | [journey-helper.php](../backend/backend/api/journey-helper.php), [documents-file.php](../backend/backend/api/documents-file.php), [test-request-linking.php](../scripts/test-request-linking.php) |
| Accounting review/link authority does not grant Treasury payment-release authority. Request completion records the authorized administrative event; a linked QR or completed custody trail is not proof of a monetary transfer. | [document-requests-update.php](../backend/backend/api/document-requests-update.php), [web/test/requests-flow.test.mjs](../web/test/requests-flow.test.mjs) |

The inspected folder/request schema does not implement a payment ledger or currency calculation. Do not invent monetary totals from folder counts. If monetary amounts become an approved requirement, specify currency and precision first, use integer minor units or an exact decimal database representation, and avoid binary floating-point arithmetic for accounting values. This is a **future rule**, not an existing implemented feature.

## Formatting, checks and review

- Web uses Oxlint with React hook checking; [web/.oxlintrc.json](../web/.oxlintrc.json) allows constant exports and warns about mixed component exports. Use targeted lint while developing; record baseline warnings rather than suppressing unrelated diagnostics.
- Mobile includes `flutter_lints`; `prefer_const_constructors` is explicitly disabled in [analysis_options.yaml](../mobile/flutter/analysis_options.yaml). Prefer `const` where useful, without making it a blanket cleanup task. Format only intentionally changed files when needed.
- PHP syntax checks do not execute endpoints and are appropriate before functional tests. There is no checked-in PHPUnit setup or demonstrated PHP style-enforcement tool.
- Run relevant checks from [TESTING.md](TESTING.md). Tests should protect user-visible behavior, contracts, permission boundaries and transaction/recovery rules. Do not add implementation-mirroring tests for trivial reversible layout edits.
- Review the diff for accidental broad formatting, generated files, secrets, session/data changes and cross-platform regressions. Record the command, date, tested environment and remaining limits; a historic passing report is not a new run.

## Protected and generated material

Do not edit `node_modules`, Flutter `.dart_tool`/`build`, web `dist`, runtime logs, uploaded files or database dumps as application source. Runtime reports/screenshots are evidence rather than specification. Existing municipal accounts/documents and saved sessions must survive routine work. Seed, reset, purge, restore, sync and legacy smoke-test scripts need explicit environment checks; they are not ordinary lint or test commands.
