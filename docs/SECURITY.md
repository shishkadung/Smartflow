## Implemented authentication and sessions

- Login uses PHP `password_verify` against stored password hashes. Signup, reset, and password change use `password_hash(..., PASSWORD_DEFAULT)` and require at least eight characters. Signup requests require admin review before an account is provisioned.
- Login issues a bearer string containing a user identifier and cryptographically random bytes, encoded as base64. It is not a JWT. SHA-256 of the complete token is stored in `auth_tokens`; validation requires a matching, unrevoked, unexpired database row. Decoding a user ID alone never establishes a session.
- Default issued session lifetime is 24 hours. Protected API calls also check that the account remains active and use `Cache-Control: no-store`. A disabled user is rejected even with an otherwise valid token.
- Browser local storage and Flutter shared preferences hold the token/user payload. Clients check `auth-session.php` periodically and clear identity after 401 or a deactivation response. Explicit logout calls `auth-logout.php`, which revokes only the presented token and safely accepts a repeated completed logout. Clients clear that login after server success; a failed logout remains actionable and must not be reported as successful server revocation.
- Reset completion locks the reset row, marks it used, updates the password, and revokes existing sessions together in a transaction. Authenticated password change also locks/revalidates the active user/session, updates the hash and revokes all existing tokens together, then returns `reauthenticate: true`. Both clients end the matching login and require sign-in with the new password. Deactivation revokes the target's tokens in its account transaction; reactivation does not un-revoke them.

## Password recovery

**19 October 2026 update (user-authorized).** Recovery email now goes through SMTP (Gmail with an App Password, TLS with certificate verification, plain SMTP only for loopback test servers) when `SMTP_HOST` is set, otherwise through the Mailtrap API; the System page shows a secret-free channel status and an administrator-only test (to the administrator's own address, three per five minutes, audited without addresses). A **backup administrator reset** exists for users whose email does not work: `users-admin-reset-password.php` (admin only; staff and head accounts only, never your own or another administrator's; active accounts only; ten per hour) issues a 12-character temporary password shown once, stored only as a hash, valid 24 hours, ending the user's sessions and unused reset codes and recording who reset whom without the password. While a temporary password is in use the API refuses every request except changing the password, session check and sign-out (`password_change_required`); choosing a new password or using an emailed code clears the flag. This deliberately differs from "codes are never returned": the temporary password is the one secret returned to an administrator, so hand it over privately and rely on the audit trail. Native clients do not yet show a forced-change screen; their user must change the password from Account & security.

Recovery generates a random six-digit code, stores its password hash, invalidates previous unused codes for that user, and sets a one-hour expiry. Reset attempts are rate limited and check active-user status and expiry. Recovery returns a generic message for missing/inactive accounts. The Mailtrap API integration verifies TLS peers/hosts; provider acceptance does not establish inbox delivery.

Password recovery always returns a generic public response without a reset code, expiry, or account-specific delivery metadata, including when maintenance is enabled. Codes are delivered through the configured email channel; clients require the user to enter the emailed code. Maintenance defaults off, requires a recognized non-production environment plus explicit `ALLOW_DEV_TOOLS=true`, and is CLI-only with an explicit operation opt-in. Normal web requests never gain maintenance access from a loopback address, an admin session, or that flag. Do not copy recovery codes into screenshots, reports, or logs.

## QR integrity and custody safeguards

The label format is `SF1.<base64url JSON>.<base64url HMAC-SHA256 signature>`. Payload fields contain document ID, issuance time, and expiry. The API checks format, signature using `hash_equals`, valid fields, expiry, and existing document. Labels are stable per folder during a 180-day lifetime; reopening or movement does not replace them. Expired labels renew when requested. The label is signed, not encrypted.

`QR_SIGNING_SECRET` can configure a random key of at least 32 bytes. Otherwise the helper generates/persists a random key in a private `.qr-secret` file under a lock. It rejects/upgrades an obsolete predictable key and attempts restrictive file permissions. Server configuration must block direct file access and preserve the key in secured backups; replacing it invalidates signatures issued with the previous key. No key-rotation/revocation list is implemented for individual labels.

For movements, the server validates supplied signed QR data and its document match. However, `qr_payload` and `scan_started_at` are optional; manual/system flows exist. When a scan timestamp is supplied, an invalid or older-than-five-minutes timestamp is rejected. These fields must not be described as a mandatory proof of a fresh physical camera scan.

Document locks serialize custody changes. Duplicate scans are checked. OUT needs a different valid receiver; only that receiver can IN after the selected OUT. Returns require a reason of at least five characters and a previous holder. Every IN/OUT now requires the displayed expected movement ID regardless of source; a scan timestamp cannot bypass that comparison. Scan can explicitly supply 0 for a legacy folder with no movement only while that absence remains current. System movements require a positive ID and explicit receipt confirmation for IN. Filed folders reject further movement. Supplied movement request IDs bind to actor, document, and payload; retries return the recorded outcome or reject mismatches/cancellation.

Sources: [QR helper](../backend/backend/api/qr-token-helper.php), [QR verify](../backend/backend/api/qr-verify.php), [movement creation](../backend/backend/api/movements-create.php), [movement helper](../backend/backend/api/movements-helper.php), [request recovery helper](../backend/backend/api/movement-requests-helper.php).

The [destination correction API](../backend/backend/api/movements-correct-destination.php) provides a separate recording-correction path for the latest unreceived OUT. It locks the same document as ordinary movement/receipt writers, validates displayed movement/destination/latest-correction IDs, appends reason and old/new destination with actor/office/time, and updates the effective destination atomically. It does not insert a custody event or alter the OUT's ID/time/counts. Filed/received/stale/wrong-office/nonstaff actions are rejected. Return corrections still target a previous holder; completed Treasury DV handling cannot use correction to bypass the optional Accounting-return constraint. A server-owned operation discriminator prevents a correction request ID from replaying an ordinary movement result. Recovery uses the existing owner-scoped movement-request protocol; this does not offer deletion, general undo, or post-receipt repair.

## Input, output, and transactional controls

- Endpoints check HTTP methods and validate required values, allowed enums, dates, IDs, lengths, destinations, and state as appropriate. PDO prepared statements bind input values; some query fragments are chosen from validated enums/integers. This source review is not an exhaustive injection audit.
- Folder creation, initial movement, signed label issuance, optional request linking and a supplied creation-operation result use a shared transaction. Schema changes are arranged before transactions because DDL can implicitly commit. Movement/recovery outcome persistence and reset-code use also have locks/transactions.
- Every request transition/link locks the request before validating state and writing. Current clients supply status plus an opaque revision covering decision/link fields, so changed state returns 409 `request_conflict`. These guards remain optional for older API callers; row locking/state validation still apply. Sequential regression checks exercise conflicts, not production concurrency stress.
- Linking and closing share category/handler-origin-or-history checks and reject replacement of a different link. Introducing a link on close also requires accepted status and handler/admin linking authority; Treasury may use an existing valid Accounting link without gaining that linking permission. Completion stores `fulfilled_by` and an office snapshot while preserving the original reviewer.
- New pull requests normalize to `general` and validate a positive existing other-office target. Stale allowed access categories from older clients cannot turn a new general pull into a DV payment-release ticket. Existing tickets and recorded creation replays are preserved; no authorization, request scope or custody state is broadened.
- Explicit named Others types override financial substring inference for routing, completion, filing eligibility, DV return controls and financial audit warnings, including tested legacy leading spaces/tabs/newlines. Financial legacy behavior and actual stored records are preserved.
- Request review, fulfillment and cancellation evidence now have separate notes, actor/time and saved office fields in the primary ticket transaction. Their fields participate in the request revision. Blank new outcome notes stay distinct from unknown legacy notes. Legacy mixed notes and available metadata are labelled generically; no office, closer or original decision is guessed. The broad direct-folder lookup adds no review/outcome-note fields in this pass.
- Folder/ticket creation accepts a random operation ID bound to actor, kind and canonical payload. Its saved result commits with the new record; same-operation replay returns that result. Owner-scoped outcome lookup reveals recorded/unknown, never another actor's result. Both clients save recovery state before POST, serialize checks/submissions and preserve newer pending IDs when delayed checks return. No automatic creation POST retry occurs after an ambiguous response. IDs remain optional for legacy callers, and advisory reference matching is not physical-folder uniqueness.
- Avatar upload is authenticated, capped at 2 MB, accepts server-detected JPEG/PNG/WebP MIME types, uses random file names and `basename` for file paths. It does not re-encode/sanitize image pixels. Photo retrieval is public for active users and cached for a day.
- Printable report values are HTML-escaped. CSV cells beginning with spreadsheet formula characters, including after whitespace, are prefixed to suppress formula evaluation.

## Rate limits and public surfaces

File-backed sliding windows use a hashed identity key and `flock` for concurrent access. Protected endpoints using `require_user_id()` default to 60 writes/minute and 240 reads/minute per validated user, separately configurable. A rejected window responds 429 with retry information. Public auth limits use remote IP and, where supplied, a normalized account identifier:

| Action | Per-IP limit per minute | Per-account limit per 15 minutes |
|---|---:|---:|
| Login | 60 | 20 |
| Signup | 10 | No account bucket in this endpoint |
| Recovery request | 10 | 5 |
| Reset attempt | 30 | 10 |

`signup-status.php` is POST-only, `no-store`, and applies a 30/minute per-IP plus 10/15-minute per-identifier limit. New signups return a 32-byte random private status key once; only its SHA-256 hash is persisted. Status lookup requires that key with the request identifier. Legacy NULL-key pending/rejected requests require a freshly entered matching username/password. Approval binds the request to the created user's immutable `approved_user_id`; approved legacy status verifies that active bound account's current username/password, not a stale signup hash or a username-matched replacement account. After rename, the request code selects the original request and current credentials prove ownership. Historical approved requests with no key and NULL account binding are not guessed/backfilled; they require administrator assistance. Missing requests and failed ownership use the same failure response. Successful lookup omits applicant full name/email and returns only owned request status/context. Both clients keep proof out of URLs and clear entered legacy passwords after checking; native async cleanup also checks the screen is still mounted. The private key remains sensitive and requires safe handling; losing it does not make the public request code sufficient proof.

Not every public endpoint uses rate limits. `offices-list.php` and active-user profile photo delivery remain public. Signup submission/login messages may still reveal account-name availability; owner-verifying status lookup is not a claim of universal account-enumeration resistance. Rate-limit files are local to one server instance, not a distributed limiter.

## Transport, server, and data handling

CORS is configured by `CORS_ALLOWED_ORIGINS`; the development default is `*`. The PHP code emits an allow-origin header only for configured origins, but CORS controls browser response access and does not replace authentication or block non-browser callers. No cookie-based auth or dedicated CSRF-token mechanism is present. Bearer transport and method/permission checks remain relevant.

Both clients now send session tokens only in authentication headers, including JSON, multipart, text/export and QR-label requests. The server accepts `Authorization` plus the existing compatibility headers and no longer reads query/body token fallbacks. Web printable labels are fetched with headers and opened as temporary Blob content rather than navigating to a token-bearing URL; native printable content/export also uses authenticated fetch. Deployments must forward one supported header. Old bookmarked token URLs no longer authenticate, and previously recorded URLs/logs are not retroactively erased by this change. Browser/shared-preference token storage remains a separate exposure boundary.

Apache [.htaccess](../backend/backend/api/.htaccess) denies dotfiles, SQL/log files, cache and log directories, and forwards authentication headers. These rules require Apache support and effective `AllowOverride`; PHP's built-in server does not enforce `.htaccess`.

Use [start-api-dev.ps1](../scripts/start-api-dev.ps1) for local PHP hosting. Its [router](../scripts/dev-router.php) binds the launcher to `127.0.0.1:8000` by default and allows only existing top-level API PHP scripts and the two public QR-label JavaScript assets. Private keys, environment files, logs/caches, SQL/backups, repository paths and traversal attempts return 404, including HEAD. The synthetic router suite passed 42 checks; local HEAD checks returned 404 for private paths, 401 for the normal protected API and 200 for label assets. XAMPP's private-key 403 remains intact. No key contents were fetched, keys rotated or application settings changed. This is a local development boundary, not production hosting certification.

Android's network security config defaults to HTTPS/system trust and allows cleartext for selected local/emulator/LAN hosts. Those exceptions are packaged in the main config, so `ENV=production` selects an HTTPS URL but does not remove the exceptions. iOS currently has broad `NSAllowsArbitraryLoads`. Production transport settings need deliberate tightening and testing.

Backend environment/key files and diagnostic logs must stay private. `.gitignore` excludes environment files, QR keys, logs, rate windows and various backup paths; exclusion is not encryption or proof that no copy exists. Diagnostic logs may contain exception context and default to debug unless configured. Audit records include actor, office, outcome, metadata, IP, user agent and time; audit write failures are swallowed so actions can still succeed. The audit trail is not immutable/tamper-evident, and complete audit persistence is not guaranteed.
