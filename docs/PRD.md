## Product purpose

The subsequent authorized [developer/session/mobile remediation](../.runtime/three-gap-remediation-report.md) blocks maintenance over HTTP and public recovery-code disclosure, isolates web views/actions across login changes, and aligns native accepted-DV release actions with the existing Treasury-or-admin rule. Launch no longer deploys or seeds automatically. Its current evidence is separate from the preceding polished-flow results.

SmartFlow helps municipal offices locate physical folders, record who received or forwarded them, follow overdue work, and review inter-office request tickets. The physical originals remain necessary. The product records custody and request handling; it does not decide the legality of a transaction, approve a DV financially, execute payment, or replace municipal signatures and supporting papers.

Pilot offices are Engineering (`ENG`), Human Resources (`HR`), Budget (`BUD`), Accounting (`ACC`), Municipal Treasury (`TRE`), and the Office of the Mayor (`MAY`). Office IDs are database values; clients should use the office list and codes rather than assume IDs.

| Department head / `head` | Office dashboard, queue, alerts and analytics; office checklists; request oversight, with clerks handling physical handoffs | Own-office monitoring and handler request decisions remain available. ## The two records must remain distinct

| Physical folder | Request ticket |
|---|---|
| `DOC-YYYY-000001` identifies a registered folder and its QR label. | `REQ-YYYY-0001` identifies requested work. |
| Registration records initial `IN` custody at the registering office. Later `IN` / `OUT` events describe physical handoffs. | States are `pending`, `approved`, `rejected`, `fulfilled`, and `cancelled`; UI wording includes Accepted, Declined, Closed, or Payment released. |
| Latest movement determines location or transfer state; route completion and filing determine whether more processing is due. | Accepting authorizes the requested work. It does not receive, forward, register, or financially approve the folder. |
| A folder can exist without a request. | A ticket can exist before a physical folder exists. An approved ticket can later link to matching folder evidence. |

Linking a folder does not complete a request or record a handoff. Several tickets may reference the same folder; the schema does not declare a one-to-one relationship. A cancelled ticket is retained but excluded from the folder's linked-request presentation. Sources: [registration](../backend/backend/api/documents-create.php), [request linking](../backend/backend/api/document-requests-helper.php), and [folder details](../backend/backend/api/documents-show.php).

## Implemented workflows

### 1. Access and account administration

An applicant submits a sign-up request. An administrator approves or rejects it; approval creates an active user. Both clients support sign-in, session validation, password recovery, profile editing, and password changes. An administrator can deactivate/reactivate an account without deleting its historical attribution; self-deactivation and deactivation of the last active admin are rejected. See [web routes](../web/src/App.jsx), [mobile routes](../mobile/flutter/lib/router.dart), [sign-up approval](../backend/backend/api/signup-approve.php), and [account status](../backend/backend/api/users-set-active.php).

The [16 October read-only audit](../.runtime/full-system-audit-2026-10-16.md) found a concurrent last-admin exception, native delayed-profile identity race and five reporting/evidence/error-state/backup finding groups. The subsequent authorized [remediation](C:/Users/nljhn/.codex/state/plugins/codex-security/scans/SmartFlow/artifacts-d1d4e1406d787ced8fe0eadea031db09727deb9cb1717568f26d45c4c687ab24/artifacts/seven-gap-remediation-2026-10-16.md) repairs all seven without changing client authority: current locked admin state and session are rechecked, native profile operations retain their originating login and saved-session pairs are written/cleared in order. Its fresh verification and device limits remain separate from the original audit.

Signup status is now an owner-verified POST: new applicants receive a private status key, while requests predating that key can use freshly entered credentials. Approval records the created user's immutable ID on the request. An approved legacy applicant uses that bound active account's current username/password; after a username change, the request code selects the original request. Another account reusing the original username gains no status access. Historical approved requests without a private key or recorded account binding require administrator assistance; no username-based backfill is guessed. A public username or request code alone reveals no applicant record. Successful logout revokes the presented server session before the client clears that login. Password changes revoke all of the user's sessions and require a new sign-in; deactivation also revokes sessions, so reactivation does not revive them. These follow-up changes are implemented in source; current verification is tracked separately from the earlier priority batch in the [follow-up report](../.runtime/system-gap-followup-report.md).

### 2. Register a folder already at the office

Staff at the holding office register an unlabelled physical folder, supply title/type and relevant logbook fields, and receive a tracking ID and signed QR label. Registration, initial `IN`, an optional approved-request link, and the supplied creation-operation result commit together or roll back together. Both clients persist an operation ID before submission and reconcile an uncertain response before another creation; explicit retries reuse the same ID and payload.

The **23 October registration clarification** makes this existing rule explicit on both clients: successful registration already records initial IN, and no second scan/IN is required for registration. Open folder is the primary success action; QR saving/printing is secondary identification. A recovered creation result describes the original registration, not verified current custody after later handoffs. Clients show the initial-IN statement only for an explicit boolean `initial_in_recorded: true`; an absent/unconfirmed flag directs staff to open the exact folder and verify custody, without recording another movement. The next inter-office handoff still requires sender OUT and the receiving office's confirmed IN. See the [implementation report](../.runtime/register-in-clarity-2026-10-23/report.md).

Current type choices depend on office: ENG/TRE/MAY offer DV; BUD offers Approved Budget; ACC offers both; HR has no fixed financial folder type. A named `Others:` folder is also supported. DV requires reference number, payee, and fund source; Approved Budget requires a reference number. An Accounting DV registration requires a different received-from office because Accounting is not the project DV originator. A supplied contents inventory requires physical-count confirmation, the main document, and at most 20 named attachments. Existing folders without inventory remain visibly unrecorded, rather than receiving guessed page counts.

Sources: [registration API](../backend/backend/api/documents-create.php), [logbook validation](../backend/backend/api/documents-logbook-helper.php), [contents validation](../backend/backend/api/folder-contents-helper.php), [web register](../web/src/pages/RegisterPage.jsx), and [mobile register](../mobile/flutter/lib/screens/shared/document_register_screen.dart).

### 3. Receive, forward, and return

Lookup by tracking ID or scan/upload a QR, inspect the folder, then explicitly record the next action. Lookup alone changes no custody. An `OUT` requires a different existing destination office and current `IN` custody at the sender. The destination office receives `IN`; it cannot receive while another office still holds the folder or receive a transfer addressed elsewhere. Every IN/OUT supplies the latest movement ID displayed for review, and the server compares it under the folder lock for Scan and Documents alike. A five-minute scan timestamp does not replace this guard. Scan may explicitly supply 0 for a legacy folder without a movement only while that absence remains current; system movements require a positive ID and receipt confirmation for IN. Clients retain that reviewed ID through confirmation rather than rebasing at submission, and Scan hides Receive for a different effective destination.

A correction return is an `OUT` to an office that previously received the folder, with a reason of at least five characters. If inventory exists, every receiving `IN` includes actual page counts; a discrepancy needs a reason. Server inventory names and requirements remain authoritative. Invalid, expired, mismatched, duplicate, and wrong-office actions return actionable errors. Movement request IDs support recovery after an uncertain response and prevent a cancelled action from arriving late.

The authorized flow simplification uses one receipt dialog in both clients: open Receive, count/check what arrived, explicitly confirm physical receipt, then record it. The earlier checkbox outside that dialog was removed. Cancelling the dialog records nothing; page counts, discrepancy reasons, displayed movement guards, recovery and staff-only authority remain required. Web Scan and Documents now reuse one handoff control, while native Documents and Scan reuse the existing destination dialog with the same suggested office and action wording. Suggestions do not become new routing constraints.

Web Scan distinguishes a confirmed saved action from its follow-up detail read. If that read fails, it keeps the saved outcome visible, marks current custody unverified and blocks another physical action until Retry successfully reloads the folder. Retrying that read never repeats the saved write.

The **19 October continuation** also serializes QR image and camera lookup: opening the image picker stops camera capture, retired camera callbacks cannot replace the image result, and another input cannot take over while image decoding/detail lookup is pending. Cancelled or failed image selection leaves camera restart explicit. Lookup still records no physical handoff. See the [continuation evidence](../.runtime/claude-continuation-2026-10-19/report.md).

The authorized **19 October mobile flow alignment** applies the same input-ownership rule to Flutter's native gallery/camera path and suppresses contradictory receive instructions on completed folders, preserving the optional final DV return. Mobile Accept/Cancel now confirm with optional review/cancellation notes; Close and Payment release use action-specific confirmation and linked-folder context, while retaining all existing authority and displayed-revision guards. Native full Folder history includes explicit `filed_by` evidence at its recorded time with unknown legacy filer preserved; computed route completion does not invent a filing event. Login error feedback and Register request references also match the current wording. See the [mobile alignment report](../.runtime/mobile-flow-alignment-2026-10-19/report.md) for fresh checks and device limits.

### 3a. Correct an unreceived OUT destination

Staff assigned to the sending office can correct a recording mistake on the latest, still-unreceived OUT. Both clients expose **Correct recorded destination** in eligible folder details. The user chooses a different receiving office, supplies a 5–1000 character reason and explicitly confirms the recording correction. This is distinct from returning an actually received folder for correction.

The API locks the folder, checks the displayed movement, destination and last correction ID, appends the old/new destination, reason, actor, sending-office snapshot and time, then updates the effective OUT destination in the same transaction. The OUT's ID, timestamp, sender, receipt contents and movement counts stay unchanged. No fake IN, extra OUT or completion is inserted. The corrected receiver sees the incoming folder; the old receiver can no longer receive it. A later receipt/movement, filed state or stale correction rejects the action. Return destinations must remain previous holders, and a completed Treasury DV retains only its allowed optional Accounting return.

Correction history remains available with the custody journey and office history. The movement-request recovery protocol persists the correction outcome; uncertain responses must be checked before an explicit retry using the saved request ID. Sources: [correction API](../backend/backend/api/movements-correct-destination.php), [correction records](../backend/backend/api/movement-corrections-helper.php), [web correction](../web/src/components/DestinationCorrection.jsx), and [mobile correction](../mobile/flutter/lib/widgets/destination_correction.dart). The follow-up passed 278 isolated API checks, 32 web tests and 103 Flutter tests; protected emulator screen review is pending user sign-in. This is not a general undo or post-receipt correction facility.

### 4. Financial folder routes and completion

The client-recorded DV route is **ENG → BUD → ACC → TRE → MAY → TRE**, with an optional return to **ACC**. The API suggests the next office from type and visited offices. It does not enforce every suggested intermediate hop as an immutable route; custody validation still controls who can send and receive.

Current route completion is derived from received history: DV is complete on latest `IN` at TRE after MAY has received it, or latest `IN` at ACC after TRE and MAY have received it. The completed TRE stage allows the optional `OUT → ACC`; other further forwarding is rejected. Approved Budget is complete on latest `IN` at ACC after BUD has received it. Eligible `Others:` folders are explicitly filed by their current staff holder. Completed folders leave active processing/overdue queues, but their history remains available.

An explicit named `Others:` type takes precedence over words such as voucher, disbursement or approved budget in its name. Such folders receive no financial route suggestion, automatic financial completion, skipped-financial-stage warning or DV-only return action; eligible staff file them explicitly. The classification also covers legacy names with leading spaces, tabs or newlines. Existing financial legacy rules remain in place, and no stored folder record is rewritten.

Explicit filing now requires the positive latest movement ID reviewed by the staff user and compares it under the folder lock. Sending and returning a folder to the same office invalidates an older File action. Native Documents and Scan retain that ID through their filing confirmation. Folder deadline edits separately lock the folder, recheck the latest acting office and compare the displayed movement and raw saved deadline; the existing head/admin deadline authority is unchanged. See the [follow-up remediation report](../.runtime/followup-remediation-report.md).

Web Documents and Scan share a filing confirmation showing the reviewed folder and the effect of filing. Cancelling records nothing; confirmation retains the displayed movement ID rather than replacing it with a fresh lookup.

**Completion of the physical trail is independent of payment release on a DV ticket.** Sources: [routing and completion predicates](../backend/backend/api/routing-helper.php), [movement completion guard](../backend/backend/api/movements-create.php), and [filing](../backend/backend/api/documents-file.php).

### 5. Request a document or inter-office work

Create a ticket with purpose and mandatory required-by date, then track it in My requests. Access requests for Budget route to BUD; DV requests route to ACC. New From office (`pull`) requests always store category `general` and use the selected existing other office, including when an older client submits a previously selected Budget/DV/Others category. By-type Others requests retain their named category and selected handler. Missing, malformed, nonexistent and self-office pull targets are rejected. Historical tickets and their saved creation-operation results retain their original category. Payroll request creation is excluded from this pilot; discovery records payslip access only, not an implemented payroll/payslip module.

The handler sees the ticket in Inbox and can accept or decline it. Decline requires a reason; both clients remind the handler to provide a separate phone/memo notice. SmartFlow does not automatically send that external notice. An accepted handler can link an existing category-matching folder or register an actual unlabelled folder with an atomic link. Linking requires handler custody history or origin evidence and cannot replace a different existing link.

For DV, ACC accepts the ticket; Treasury's inbox includes accepted DV tickets for actual payment-release recording. Only Treasury or an admin may close an accepted DV ticket. For other categories, the API permits the handler/admin to fulfill a pending or accepted ticket. A requester/admin can cancel a pending or accepted ticket. Pending and accepted tickets remain overdue after the required-by date until closed, declined, or cancelled; the due day itself is included.

Every request decision/link now validates authoritative state under a row lock. Current web/mobile actions send the displayed status and revision; changed tickets return a conflict for review. Closing cannot bypass the same category, handler evidence, accepted-status and nonreplacement checks when introducing a folder link. Treasury may close an already valid linked DV without acquiring Accounting linking authority. Completion stores the actor and office separately from the original reviewer; Treasury-fulfilled DV tickets remain in its inbox using that recorded office evidence. Legacy completions with no recorded closer are not assigned guessed attribution.

Cancellation and completion now preserve the full initial review notes, reviewer and review time, recording their own notes, actor, office snapshot and time separately in the ticket transaction. Both clients show those stages separately. Older mixed notes and their available recorded actor/time remain visible under a generic label explaining that their stage is unknown; no historical review or outcome is reconstructed. Web decisions, linking and register-from-request remain disabled until the selected exact ticket has loaded successfully; a successful list refresh alone cannot restore those actions. See the [follow-up remediation report](../.runtime/followup-remediation-report.md).

Requests use server pagination, status/overdue/search filters and whole-view counts. Exact-ID lookup remains office/requester scoped and can open an older permitted ticket independently of the selected page or filters. Creation recovery covers ticket creation as well as folder registration.

After a new or recovered creation, both clients reveal that exact permitted ticket even when the previous list filters would hide it, while retaining a return to the previous request view. Native rows and counts belong to their loaded account/tab/filter/search/page query. A failed changed-query read cannot present the previous query's records or totals; failed refreshes keep same-query data visibly stale and block decisions until a successful read. These client rules preserve server scope, revisions and role authority.

The primary linked-folder action now opens that exact folder in Documents on both clients; custody history remains a separate secondary action. Eligible own-office staff see the usual confirmed actions. When a linked folder is outside an office tray, a 404 from that tray lookup can fall back to the existing authenticated tracking endpoints and render read-only detail. A 403 is never bypassed. This navigation change grants no additional custody or visibility permission.

Linked-folder details now include **Back to request**. Web commits the Requests tab, filter, search, page and selected ticket to validated URL parameters, so returning restores the same view and exact selection even when the ticket lies outside that page/filter. Unsubmitted search text is not committed. Native keeps the Requests screen beneath the pushed Documents screen, then refreshes the ticket before reopening its full details. This retains context without replaying an old decision or altering request state.

## Acceptance criteria for future changes

These are review requirements, not a claim of a fresh test run on this document's date. Executable checks and recorded evidence belong in [TESTING.md](TESTING.md).

| Area | Acceptance condition |
|---|---|
| Custody separation | Accepting, linking, completing, or cancelling a request cannot insert an `IN`/`OUT`; lookup cannot move a folder. |
| Registration | Correct holder/logbook/type validation; exactly one initial `IN`; invalid request linking rolls back folder, movement, and link. |
| Handoffs | Reject wrong sender/receiver, duplicate, stale, same-office and missing-destination actions; preserve the last valid custody state. |
| Destination recording correction | Only sending-office staff can correct the latest unreceived OUT; retain original event identity/time/counts and append old/new destination, reason and actor. Reject stale or received state; preserve return/completion constraints and recover uncertain outcomes. |
| Returns and contents | Preserve a complete return reason and receiving counts; reject unknown inventory IDs and unconfirmed receipts; retain legacy unrecorded contents honestly. |
| Routes | Verify ENG→BUD→ACC→TRE→MAY→TRE→optional ACC, a correction return, Budget completion at ACC, and staff-only filing of an Others folder. |
| Requests | Required date and full purpose/review notes remain visible; accepted overdue tickets stay overdue; DV completion requires accepted status and Treasury/admin authorization. |
| Roles | Head/admin custody views remain read-only and API registration/IN/OUT/filing deny nonstaff. Preserve request/checklist/deadline authority; staff custody writes enforce the assigned office; exports require Accounting admin. |
| Reliability | Failed loads show errors/retry; uncertain creation/movement results are reconciled before retry; creation retries reuse their saved ID/payload; stale request decisions cannot overwrite a changed revision. |
| Account privacy and sessions | Signup status requires owner proof; authenticated tokens stay in headers including exports/labels. Logout revokes the presented session; password change/deactivation revoke existing sessions; changed-password users sign in again. |
| Linked-folder navigation | Requests opens exact Documents detail with history secondary; out-of-tray fallback is read-only and only follows a 404, never a permission denial. |
| UI | Verify actual web and emulator screens, empty/loaded/error/busy states, small phones, large text, keyboard focus, scrolling, and persistent action visibility. Passing a build is insufficient visual acceptance. |
| Data preservation | Tests use isolated databases or in-memory fixtures. Existing users, sessions, and operational records are preserved. |

## Non-goals and boundaries

- Financial approval, appropriation validation, accounting entries, bank/check issuance, payment execution, and electronic signatures.
- Replacing original physical documents or automatically certifying contents against COA requirements.
- A payroll calculation or payslip-delivery module in the current pilot.
- A fully offline custody-write mode. Recovery from uncertainty is implemented; an authoritative handoff still needs the API.
- External notice delivery, automatic email/SMS/push follow-up, or a retention/destruction scheduler unless separately specified and verified.
- A mandatory universal attachment checklist. Office heads/admins publish local requirements; staff count actual pages.
